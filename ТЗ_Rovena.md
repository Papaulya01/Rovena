## 1. Суть проекта

Система из трёх приложений, работающих поверх общего слоя бизнес-логики (см. раздел 2) и Radmin — программы удалённого доступа (Radmin VPN), которая соединяет CRM и Staff в одну виртуальную сеть, когда они физически не в одном месте (см. п.2.6). *Изначально в ТЗ Radmin был записан как "внешний API с товарами/остатками" — это была ошибка формулировки на старте; по факту речь всегда шла про Radmin VPN, см. историю изменений за 27.08.2026.*

| Компонент | Кто использует | Устройство | Роль |
|---|---|---|---|
| **Rovena-Staff** | Сотрудник в точке (кассир/официант) | Моноблок | Приём заказов/броней на месте, доставка. **Уточнено 29–30.08.2026: реализуется не отдельным приложением, а как панель роли `cashier` внутри Rovena-CRM** (тот же процесс, та же БД) — см. 4.10. |
| **Rovena-CRM** | Админ | Ноутбук | Управление: заказы, брони, доход/расход, бухгалтерия, отчётность |
| **Rovena-Bot** | Клиент | Телеграм (бот или Mini App) | Просмотр, бронь, заказ, доставка со стороны клиента |

Все три — это разные интерфейсы (UI) над одним и тем же ядром данных. Ядро агрегирует данные от Staff и Bot и стекается в CRM для бухгалтерии и отчётности.

## 2. Архитектурные решения (принято в обсуждении)

1. **Единый backend-слой** между Radmin API и тремя клиентами — обязателен. Staff и Bot не должны ходить в Radmin API напрямую и не должны дублировать бизнес-логику каждый по-своему. Причины:
   - гонки при одновременной записи (staff и клиент бронируют одно и то же одновременно);
   - расхождение бизнес-логики между клиентами (скидки, расчёты);
   - невозможность вести единый аудит-лог по всем источникам.
2. **Единая сущность "движение денег"** (`finance_entries`) — и приход (заказ через Staff/Bot/CRM), и расход (закупки, ручные записи) — всё в одном формате: тип, сумма, источник, автор, время, привязка к заказу. Без этого отчётность будет собираться костылями из разнородных данных.
3. **Разделение доступа по источникам, а не по сети.** Правильный уровень изоляции — не физическая сеть (VLAN/VPN), а отдельные API-ключи/токены на каждого клиента (Staff / Bot / CRM) со своими правами (scopes):
   - Staff: может писать заказы/брони, **не видит** бухгалтерию/отчётность;
   - Bot: может создавать заявки от клиента, **не может** редактировать чужие заказы, не видит финансы;
   - CRM: полный доступ (пишет и читает всё), управляет ключами остальных.
   Сетевая изоляция (VPN между точкой и сервером) — опциональный **дополнительный** слой поверх авторизации, а не замена ей.
4. **Управление подключениями централизовано в CRM** — раздел "Подключения": статус (online/offline), возможность перевыпустить/отозвать ключ отдельного клиента без остановки остальных, лог запросов по каждому источнику.
5. Каждая запись (заказ, бронь, финансовая операция) хранит `source` (`staff` / `bot` / `crm`) — чтобы всегда было видно, откуда пришли данные.
6. **Radmin VPN — сетевой транспорт для случая "CRM не в той же сети, что точка".** Уточнено 27.08.2026: если ноутбук админа физически не в точке продаж (например, дома), для связи Staff↔CRM используется Radmin VPN — сторонняя программа удалённого доступа, ставится на оба устройства, создаёт общую виртуальную сеть (обычно адреса вида `26.x.x.x`). CRM ничего специально не настраивает для неё — просто слушает на всех сетевых интерфейсах, и как только Radmin VPN подключён, его адрес автоматически появляется в «Подключения → Rovena-Staff» с пометкой. Условие для работы всегда одно: **CRM должна быть запущена** (сервер поднимается сам при старте CRM, если раз включён — см. 4.5).

## 3. Технологический стек

- **Rovena-CRM**: React + Electron (`electron-vite`) + SQLite (`better-sqlite3`) — desktop-приложение под ноутбук админа.
- **Rovena-Staff**: тот же стек (React + Electron), UI урезан под точку продаж (без бухгалтерии/отчётности) — *ещё не начато*.
- **Rovena-Bot**: Telegram-бот; решение по формату (обычный бот vs Mini App) — *см. открытые вопросы*.
- **Backend / ядро**: на первом этапе живёт встроенным в Rovena-CRM — Electron main process поднимает HTTP-сервер (Express) поверх той же SQLite и бизнес-логики, что использует сама CRM (`src/main/repo.js`). Отдельный масштабируемый сервис — *см. открытые вопросы*.
- **БД в CRM (локально)**: SQLite. Для общего backend'а обсуждался вариант PostgreSQL, но решение не принято.

## 4. Сделано на сегодня

### 4.1 Rovena-CRM — стартовая сборка ✅

Стек: React + Electron (electron-vite) + SQLite (better-sqlite3). Проверено: `npm install` и `electron-vite build` проходят без ошибок.

**Реализованные сущности (SQLite):**

- `bookings` — брони: клиент, даты, статус (`new/confirmed/cancelled/done`), источник.
- `orders` + `order_items` — заказы: клиент, доставка (да/нет), позиции, сумма, статус, источник.
- `finance_entries` — единая лента доход/расход, с привязкой к заказу, источнику и автору.
- `connections` — настройки подключений: `radmin_api`, `rovena_staff`, `rovena_bot` (base URL, ключ, статус).
- `audit_log` — история изменений (entity, action, автор, время).

**Реализованные экраны (React):**

- Обзор (сводка доход/расход/баланс, последние заказы и брони).
- Брони — список + создание + подтверждение.
- Заказы — список + создание с позициями + завершение.
- Бухгалтерия — лента операций + сводка + ручное добавление записи.
- Подключения — управление base URL / ключом для Radmin API / Staff / Bot по отдельности.

**Безопасность:** `contextIsolation: true`, `nodeIntegration: false` — renderer не имеет прямого доступа к Node.js/файловой системе, только через явный `window.rovena.*` API из preload.

**Чего в сборке нет (осознанно, задел на будущее):**
- Реального клиента к Radmin API (сейчас только хранилище настроек подключения, запросов ещё нет).
- Синхронизации данных от Staff/Bot — сейчас все записи создаются только локально из CRM.
- Ролей и прав доступа внутри самой CRM (один админ без разделения).
- Автоматического health-check статуса подключений (`online`/`offline` не обновляется сам).

### 4.2 CRM как сервер для Staff, управляемый бот, каталог, помесячная отчётность ✅

**Общий слой бизнес-логики вынесен в `src/main/repo.js`** — и IPC-хендлеры самой CRM, и HTTP-сервер для Staff, и бот теперь вызывают одни и те же функции работы с БД, а не дублируют SQL (прямое следствие архитектурного решения №1).

**Встроенный HTTP-сервер (`src/main/server.js`, Express) — CRM выступает сервером для Rovena-Staff:**
- Включается/выключается из раздела «Подключения», порт настраивается (по умолчанию 4780).
- Авторизация по Bearer-токену (`connections.rovena_staff.api_key`), ключ можно перевыпустить одной кнопкой.
- Публичный `GET /health` для проверки доступности; `/api/menu`, `/api/categories`, `/api/bookings`, `/api/orders` (GET/POST/PATCH) — под токеном. Бухгалтерия сюда сознательно не отдаётся (Staff её не видит — п.3 архитектуры).
- При каждом успешном запросе с валидным токеном статус подключения обновляется на `online`.
- Проверено вручную end-to-end (health-check, 401 без токена, чтение каталога и создание брони с токеном).

**Управляемый Telegram-бот (`src/main/bot.js`), long-polling без внешних зависимостей (`fetch`/`AbortController` из Node):**
- Запуск/остановка из «Подключения» по токену от @BotFather, статус и username видны в UI.
- MVP-команды: `/start`, `/menu` (показывает актуальный каталог CRM), `/help`. Приём заказов/броней через бота — сознательно не делали, зависит от открытого вопроса «обычный бот vs Mini App».

**Каталог (`categories` + `menu_items`), новый раздел «Меню»:** CRM централизованно ведёт категории и позиции с ценами; их видят Staff (через сервер) и бот (`/menu`); при создании заказа в CRM позиции теперь можно выбирать из каталога (подставляются название/цена, снимок сохраняется в `order_items`).

**Брони:** добавлено поле `purpose` (цель брони), даты выводятся в читаемом виде (`formatDateTime`), диапазон "с – по" остаётся `datetime-local` (дата и время, не только дата).

**Бухгалтерия переработана:** помесячная сводка доход/расход/баланс (`finance:monthly`, график по месяцам), разбивка расходов по категориям за текущий месяц (`finance:categoryBreakdown`), суммы везде через единый форматтер (`formatMoney`, разряды пробелом).

**Маски ввода (`src/renderer/src/utils/format.js`):** телефон форматируется по мере набора (учитывает `998`/`7`/`8` как код страны), цена/сумма — с группировкой тысяч, оба поля хранят и передают чистое число.

**UI «Подключения» переведён на аккордеон** — три сворачиваемых блока (Radmin API / Rovena-Staff / Rovena-Bot), у каждого своя инструкция прямо в интерфейсе (как получить токен бота, как подключить Staff к серверу CRM, как работает проверка Radmin).

**Лого и иконка:** сгенерирована процедурно (монограмма "R", тёмно-зелёный + золотой — фирменные цвета из `styles.css`), без внешних зависимостей — `resources/icon.ico`/`icon.png` (иконка приложения и таскбара) и `src/renderer/public/favicon.ico`/`logo.png` (фавикон и лого в сайдбаре).

**Чего всё ещё нет (сознательно, следующие шаги):**
- Приёма заказов/броней через бота (см. открытый вопрос про формат бота).
- Rovena-Staff как отдельного приложения — сервер для него готов, но клиента пока нет.
- Реальной синхронизации с Radmin API (пока только проверка доступности base URL).
- Автозапуска сервера/бота при старте CRM (сейчас ручной старт/стоп в «Подключениях»).

### 4.3 Столы, доработка иконки/UI, важный фикс хранения данных ✅

**Столы (`tables`)** — новая сущность зала: название, вместимость, зона. Отдельный раздел «Столы» в CRM (CRUD), брони теперь ссылаются на конкретный стол (`bookings.table_id`, выбор из выпадающего списка вместо только текста), Staff получает список через `GET /api/tables`, бот — командой `/tables`.

**Важный фикс: данные "пропадали" после перезапуска.** Причина найдена и устранена — без явного `app.setName()` Electron в части сценариев запуска не мог определить имя приложения из package.json и откатывался на generic `"Electron"`, из-за чего папка с БД (`userData`) уезжала в другое место (`%APPDATA%\Electron\` вместо `%APPDATA%\rovena-crm\`) в зависимости от того, как именно был запущен процесс. Теперь имя и путь к `userData` зафиксированы явно в коде (`src/main/index.js`), плюс добавлен `app.requestSingleInstanceLock()` — второй запуск поднимает окно первого вместо того, чтобы два процесса писали в один SQLite-файл одновременно. Проверено: несколько циклов «записать → полностью закрыть → перезапустить другим способом → прочитать» — данные на месте, БД стабильно в одной и той же папке.

**Иконка приложения переработана** — более собранные пропорции монограммы "R", лёгкий градиент для объёма.

**Навигация в сайдбаре получила иконки** (`src/renderer/src/components/icons.jsx`) — простые линейные SVG-компоненты на каждый раздел, наследуют цвет текста (авто-подхватывают состояния hover/active).

**Чекбоксы, радиокнопки и select приведены к общему дизайну** (`styles.css`) — кастомный чек/радио вместо системных, у select — свой шеврон вместо браузерного.

### 4.4 Живой статус столов на «Обзоре», иконка по референсу ✅

**Статус столов прямо на главной.** Раздел «Столы сейчас» на «Обзоре» показывает каждый активный стол карточкой: свободен / бронь (в ближайшие 6 часов) / занят (бронь идёт прямо сейчас), с именем клиента и временем. Логика — `repo.tableStatuses()`, обновляется каждые 30 сек. При первой версии было расхождение часовых поясов (сравнивали локальное время брони с UTC-датой) — из-за этого бронь через несколько часов не подсвечивалась; поправлено на скользящее окно в 6 часов от текущего момента, оба сравнения теперь в одном (локальном) времени. Также отдано наружу: `GET /api/tables/status` для Staff.

**Иконка переделана по референсу пользователя** — фиолетово-индиговый градиент с мягкими диагональными световыми полосами (вместо тёмно-зелёного фона) и золотая монограмма в виде цветка/короны из лепестков над стеблем "R" с завитком на хвостике (вместо простой геометрической буквы). Технически: те же самые процедурные PNG/ICO без внешних зависимостей, просто более сложная геометрия (vesica-лепестки через пересечение окружностей) и two-tone металлический градиент золота. Точь-в-точь фотореалистичный референс (стекло/блики) не воспроизвести без инструмента генерации изображений — сделана аккуратная векторная интерпретация в том же духе.

*Заметка:* сайдбар и остальной UI остались в прежней тёмно-зелёной палитре — новый фиолетовый только у иконки/фавикона, чтобы не менять фирменный стиль без отдельного запроса.

Это прямое условие для сценария «ноутбук дома, Radmin VPN включён» — Staff должен достучаться сразу, как только CRM открылась, без ручных действий. Проверено: включили один раз → полностью закрыли процесс → запустили заново другим способом → сервер поднялся сам.

**Radmin VPN подключение реально работает уже сейчас** — Radmin VPN на этой машине создаёт сетевой адрес `26.x.x.x`, `os.networkInterfaces()` видит его как обычный интерфейс, и CRM (слушает на всех интерфейсах) уже отдавала этот адрес в списке для Staff, просто без пометки. Теперь адрес помечается явно («через Radmin VPN — работает из любой сети» / «локальная сеть»), в инструкции добавлен шаг с Radmin VPN и предупреждение про брандмауэр Windows (первый запуск сервера может потребовать разрешить доступ, включая «общественные» сети — иначе VPN-адрес не будет отвечать).

- В позициях заказа не было кнопки удаления строки — добавлена (крестик рядом с ценой).

- **Заменили нативный `<select>` на собственный компонент** (`src/renderer/src/components/Select.jsx`) везде, где он есть (стол в брони, категория и позиция меню, тип в бухгалтерии). Кастомный компонент сам рисует и закрытое поле, и список, полностью под общий стиль.

### 4.6 Важное уточнение роли CRM: только контроль, не создание ⚠️ (меняет модель использования)

**Уточнено пользователем 27.08.2026, сделано в тот же день.** CRM — это **пункт контроля, база данных и бухгалтерия**, а не место, где вручную заводят заказы и брони. Реальный сценарий: Staff (моноблок в точке) и Bot принимают заказы/брони от гостей; CRM в реальном времени **показывает**, что происходит — какой стол занят, что на нём готовится/заказано, кто и на что забронировал, — и даёт инструменты контроля (сменить статус, закрыть чек) и отчётности. ### 4.11 Бухгалтерская отчётность, налоговые настройки, живые часы, печать чеков ✅

### 4.20 Полная логика Rovena-Bot (регистрация, заказы, брони, доставка) ✅

**Задача пользователя (30.08.2026)**: «пиши максимальную логику бота, кнопки быстрых действий, при входе в бот — выбрать язык, после инструкция по использованию, после на выбор регистрировать себя / обычный заказ / бронирование; посмотреть столы, посмотреть меню, выбрать стол, забронировать и сделать сразу заказ, указать время прибытия или просто забронировать или заказать доставку; оплата пока только наличкой, в дальнейшем по QR — вывести настройки этого в подключения бота; уведомления продумать; в Staff показывать брони на стол».

Бот (`src/main/bot.js`, переписан полностью) — теперь полноценный сценарий на кнопках (`ReplyKeyboardMarkup` — постоянное меню быстрых действий снизу — плюс `InlineKeyboardMarkup` для контекстных шагов), с состоянием диалога в памяти процесса (`sessions`, переживает только текущий запуск бота — не БД). Тексты бота вынесены в отдельный серверный словарь `src/main/botMessages.js` на 3 языках (RU/UZ-латиница/UZ-кириллица) — отдельно от `src/renderer/src/i18n`, так как у бота (главный процесс) нет доступа к рендереру.

**Сценарий:**
1. `/start` у нового гостя → выбор языка (инлайн-кнопки, сразу на всех 3 языках, чтобы гость мог прочитать хоть один) → инструкция по кнопкам → главное меню.
2. Главное меню (кнопки снизу): «Регистрация», «Сделать заказ», «Забронировать стол», «Столы», «Меню», «Язык», «Помощь». Регистрация запоминает имя и телефон (через кнопку «Поделиться контактом» или вручную) в новой таблице `bot_customers` — чтобы не спрашивать заново при следующих заказах.
3. «Сделать заказ» → «В зале» (выбор стола из живого статуса — 🟢/🟡/🔴, тот же `tableStatuses`, что видит и Staff) или «Доставка» (адрес одним сообщением) → меню (категории → блюда, инлайн-корзина с live-редактированием сообщения и счётчиком «Готово (N)») → время («Сейчас», +30/+60/+120 минут, или вручную ЧЧ:ММ) — для доставки шаг времени пропускается (всегда «как можно скорее», без отдельного поля под желаемое время доставки — сознательно упрощено для MVP) → подтверждение с итогом заказа и пометкой об оплате наличными (или наличными+QR, если QR загружен в настройках) → создаётся бронь (если указано время прихода) и/или заказ.
4. «Забронировать стол» → «Бронь + заказ» (тот же путь, что и «В зале» выше) или «Только бронь» (стол → время, без меню) → создаётся `bookings` со `status='new'`.
5. Заказ, оформленный «сейчас» (без будущего времени), сразу привязывается к открытой смене (`shift_id`), если она есть, — и тут же появляется в «Заказы этой смены» у кассира, как обычный заказ Staff.

**Интеграция с существующей схемой** — намеренно переиспользованы, а не задублированы, существующие таблицы `bookings`/`orders` (в них уже были поля `source: 'bot'`, `booking_id`, `delivery`, `client_name/contact` — заложены ещё 27.08.2026 при проектировании архитектуры). Добавлены новые колонки: `orders.payment_method` (`cash`|`qr`, пока всегда `cash`), `orders.delivery_address`, `orders.bot_chat_id`, `bookings.bot_chat_id`, `bookings.reminder_sent`; новые таблицы `bot_customers` (язык/имя/телефон гостя) и `bot_settings` (QR, chat_id и переключатели уведомлений, минуты напоминания).

**Оплата**: только наличными на месте, как и просил пользователь. Добавлена возможность загрузить QR-код в «Подключения → Бот → Настройки бота» — гость увидит его при подтверждении заказа с пометкой «в будущем — по QR», но сам приём онлайн-оплаты не реализован (это отдельная, следующая по счёту задача — эквайринг/Telegram Payments).

**Уведомления (автоматические, продумано по просьбе пользователя):**
- Гостю — мгновенное подтверждение брони/заказа в чат сразу после оформления.
- Гостю — напоминание за N минут до брони (настраивается в «Подключения → Бот», по умолчанию 60 минут, 0 — выключить); проверяется раз в минуту, отмечается `reminder_sent`, чтобы не продублировать.
- Гостю — уведомление, когда Staff/CRM меняет статус его заказа на «Готово»/«Отменён» или брони на «Подтверждена»/«Отменена» (подключено в `ipcHandlers.js` к тем же обработчикам `orders:update`/`bookings:update`, которыми пользуются и панель кассира, и админ «Брони»/«Заказы» — не отдельный путь).
- Персоналу — уведомление в Telegram о каждой новой брони/заказе от бота, если в настройках указан `chat_id` (узнать свой chat_id можно командой `/id` — бот пришлёт число) и включён соответствующий переключатель.

**Staff/панель кассира**: карточка стола в панели кассира теперь показывает не только цвет статуса (свободен/бронь/занят — это уже работало), но и имя гостя и время брони под названием стола, если бронь есть — то, что просил пользователь проверить после создания тестового Staff-пользователя.

**Не реализовано намеренно (зафиксировано как сознательные границы MVP, не забытое):**
- Состояние диалога бота живёт только в памяти процесса — перезапуск бота (не CRM в целом) сбрасывает гостя на середине оформления к главному меню; регистрация и все уже созданные брони/заказы в БД не теряются.
- Бот по-прежнему общий на все заведения (первое активное) — мультиточечная маршрутизация бота отдельно не решена, см. открытые вопросы.
- Реального приёма онлайн-оплаты нет — только показ QR как задел.
- Сценарий не протестирован сквозным CDP-тестом против настоящего Telegram (в отличие от остальных фич этой сессии) — тестирование требует реального токена бота пользователя и означало бы отправку настоящих сообщений в Telegram, поэтому оставлено пользователю. Код прошёл ручной построчный разбор на логические ошибки (в процессе найдены и исправлены два реальных бага: `createBooking`/`createOrder` в `repo.js` не сохраняли часть новых колонок, включая `bot_chat_id`, из-за неполного списка колонок в INSERT; часть сообщений бота могла ломаться при отправке, если гость вводит в имя/адрес символы `<`, `&` — HTML-разметка сообщений сделана точечной, а не сквозной) — и успешно собран (`npm run build`), IPC-цепочка настроек бота (`botSettings:get/update`) проверена сквозным тестом через реальный CRM.
  **Обновление того же дня — пользователь начал живое тестирование с реальным ботом** и по ходу прислал ряд доработок, все реализованы:
  - **Проверка брони при выборе времени** — `repo.findBookingConflict(tableId, dateFromIso)` сравнивает условное 2-часовое окно новой брони с уже существующими активными бронями на этот стол; для варианта «сейчас» проверяется живой статус стола (`tableStatuses`). При конфликте гостю показывается сообщение с временем занятости и кнопки «Выбрать другое время» / «Выбрать другой стол» вместо тихого создания дублирующей брони.
  - **История заказов гостя с повтором** — новая кнопка «🕘 История заказов» показывает последние заказы этого чата (`repo.listBotOrderHistory`, по `orders.bot_chat_id`) с суммой и составом; кнопка «повторить» копирует ещё доступные в меню позиции в новую корзину (сняты с продажи блюда — пропускаются с предупреждением) и продолжает обычный сценарий оформления с актуальными ценами.
  - **Мои брони + отмена с причиной** — кнопка «📅 Мои брони» показывает активные брони гостя (`repo.listBotBookings`); по каждой можно посмотреть детали и отменить, при отмене бот спрашивает причину одним сообщением (необязательно, можно пропустить кнопкой «Без причины») — причина сохраняется в `bookings.comment`, персоналу приходит уведомление об отмене с указанием причины.
  - **Геолокация для доставки** — при заказе с доставкой рядом с полем адреса теперь есть кнопка «📍 Отправить геолокацию» (нативная функция Telegram); если гость делится геопозицией, адрес сохраняется как ссылка на карту (`https://maps.google.com/?q=...`) вместо текста, минуя необходимость печатать адрес руками.
  - **Кнопка «Связаться с клиентом»** — во всех уведомлениях персоналу (новая бронь, новый заказ, отмена брони гостем) добавлена инлайн-кнопка: открывает `tel:` (если у гостя есть телефон из регистрации) или `tg://user?id=...` (диплинк в Telegram по chat_id), чтобы не искать контакт вручную.
  - Заодно исправлена видимость данных доставки в самой CRM: страница «Заказы» показывала «Да/Нет» для доставки без адреса и не показывала телефон/контакт клиента вообще — теперь адрес доставки (или ссылка на геолокацию) выводится прямо в таблице, а под именем клиента показывается его контакт; статус заказа тоже переведён на человекочитаемый (было сырое `new`/`done` из БД).
